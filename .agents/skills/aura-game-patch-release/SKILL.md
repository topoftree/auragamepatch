# Aura 游戏补丁发布

用户已于 2026-10-23 明确要求：以后产生新的游戏专用兼容／修复补丁，自动打包上传到 `topoftree/auragamepatch`，做好分类与 App 对应的自动下载安装、启用程序。这是该范围内持续有效的发布授权；满足下述证据与检查后直接完成，不重复请求发布确认。用户后续更具体的要求优先。

这不是后台任务。后续 Codex 在 Aura 项目中处理相关修改时，先读取本 skill 并执行。缺少源码、签名密钥、网络或实际验证条件时如实报告具体缺口；完成其他可执行工作，不假报发布或游戏效果。

## 1. 确认修复范围

1. 读取项目 `AGENTS.md`、[工作流与协议](references/workflow.md)，以及应用的 `docs/GAME_PATCH_DOWNLOADS.md`。检查两个仓库的工作树与远端，保留用户改动。
2. 明确问题、实际游戏、启动 EXE、架构、发行版本、原文件大小／SHA-256、复现证据与预期行为。Steam ID 可作检索信息；Local 封面 ID 不能决定游戏身份。游戏文件和用户诊断只在本地分析。
3. 区分通用修复与专用修复。通用的内存、呈现、同步或驱动修复留在运行时；特定 EXE 的字节修改、版本适配、配置、模组才进补丁仓库。需要配套运行时能力时，一并完成能力与测试，明确最低 App 版本。
4. 按 `game → category → patch-id → version` 保存配方。分类只能为 `compatibility`、`fix`、`widescreen`、`mod`、`tool`。不能为了自动安装把 FPS 模组或交互工具改标为 fix。

## 2. 制作可复现的包

使用现有声明式 manifest：`binary`（精确字节配方）、`files`（相对真实 EXE 复制）、`profile`（App 白名单配置）或 `tool`（仅工具文件）。不加入下载脚本执行器、任意命令、绝对路径、游戏根目录外写入或未经支持的启动参数。

- 包放 `packages/<id>/<version>.zip`，已发布版本不可覆盖。源码、上游来源、许可证、验证记录随仓库保存，遵循原许可证的对应源码义务。
- 只公开必要补丁配方和可再分发组件；不上传完整游戏 EXE／资源、账号凭证、原始诊断、APK 签名、目录私钥、R8 mapping 或独立 App 原源码。
- 二进制修改要求完整前后 SHA-256、文件大小、每处旧字节和新字节；不能用文件名代替版本校验。
- 不新增虚构补丁、假测试或为了演示发布的测试包。临时测试夹具不进入公开目录。

## 3. 完成 App 接入

阅读并使用 `GamePatchCatalog`、`GamePatchPackage`、`GamePatchRepository`、`GamePatchFiles`、`InstalledGamePatchPolicy` 与 `GamePatchAutomatic`。不能只上传 ZIP 然后声称 App 已支持。

- `catalog-v2.json` 与 `catalog-v2.sig` 是分类和自动安装协议；`catalog.json` / `catalog.sig` 保持旧客户端兼容，不向严格 v1 解码器塞入新字段。
- 仅经过检查的兼容／错误修复可声明 `autoInstall`。必须给出最低 App versionCode、精确 EXE 基线和全部目标文件原始基线（`before: null` 表示必须不存在）。启动前匹配、下载、验签验哈希，再取得存储租约、重新验证并安装启用。
- 已安装版本不自动替换；关闭、卸载或删除过的补丁不自动重新启用或下载。中断事务先恢复，游戏运行时不改文件或会话快照。离线、超时或不匹配保留原游戏，记录原因，并让用户在 Library → 游戏介绍 → Patch 重试下载或 Import patch。
- 包需要新配置键、DLL 加载或加载器依赖时，增加**窄范围、按游戏限制**的 App 支持、启动快照和测试，更新工具白名单与最低版本，禁止静默忽略未知键。不存在通用“下载后执行安装器”。
- BF3 单人模式、宽屏、FPS 解锁、实验模组和交互工具继续用户选择。SMAPI 仅在用户已启用依赖模组时自动补齐。不得自动跳过影片、改变游戏速度、客户端授权或联机语义。
- 下载记录进入现有 Patch 管理。关闭恢复原状态；卸载保留离线包；删除清除 Aura 副本；旧文件备份只留设备上。文件冲突、中断恢复、用户手动优先、Steam／Local 隔离必须保留。

## 4. 验证和发布

1. 执行与补丁有关的安装／启用／关闭／卸载／删除／恢复、未知版本拒绝、冲突、重复安装、手动覆盖和网络失败检查。自动安装还需核验实际启动调用点与最低版本门槛。真实游戏效果与宿主测试分别记录。
2. 运行 `tools/patch_release.py add` 制作确定性包、签 v2 目录并更新分类；命令见 reference。旧的 `build_catalog.py` 是历史全量生成器，**不得用它添加新游戏**，避免覆盖历史目录。
3. 运行 `tools/patch_release.py check`，检查公开 diff、分类、说明、对应源码／许可和验证证据。用项目实际公钥验签；私钥只从仓库外读取，不上传、不打印、不自动轮换。
4. 更新补丁仓库 README / CHANGELOG 以及 App 中文 CHANGELOG、协议文档和必要 AGENTS 约定。先本地提交经过测试的 App 变化；将提交号写入自动补丁验证记录。
5. 在干净、已审阅的补丁分支使用 `tools/patch_release.py publish`，推送 `topoftree/auragamepatch/main`，按远端提交逐文件下载比对哈希。若并发推送冲突，先获取并核对，不强推。
6. 不因本 skill 自动生成 APK、发布到 `topoftree/Aura` 或推送私有 App 源码；这些仍遵守用户当次明确要求。App 新能力未交付时说明“仓库已发布；自动功能需后续新版 APK”，不能声称用户已安装版本立即拥有它。

完成后给出补丁仓库提交／目录链接、适用游戏版本、自动或手动策略、验证结果及尚未真机确认的部分。发布失败保留本地成果并说明具体失败步骤。
